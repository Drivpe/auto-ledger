# 06 — 前置闸门：账簿与账页的三个未闭合

**What to build:** 三个会直接改写实现方案的平台事实被实测闭合，并留下可复跑的取证记录。这三个没闭合之前，「一个一级科目一本账簿 + 逐个建账页」的地基就是悬空的。

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

- [ ] 闭合一：一本账簿能否容纳同一一级科目下的**多个账页**（如 1002 下的 100201–100204）。这决定账簿数是否真的落在 55
- [ ] 闭合二：账簿名称重复是否被平台拒绝。55 本需要各自唯一命名
- [ ] 闭合三：账页标识（平台内部 ID）从何而来（服务端生成 / 按科目序）。已知「账簿 ID」与「账页 ID」是两个不同值域，对应关系需确证
- [ ] 顺带一测：平台的「自动建账簿」按钮能否把全部明细科目账页一次开全；结论只记录，不据此改方案（省不省这步由后续工单决定）
- [ ] 登记两条不阻断但需留档的观察：凭证里明细科目为空的行在打勾时勾哪一行；一月任务是否需要年结线（写入曾被「上月未结账，不可输入下月记录」拒绝）
- [ ] 每条闭合都留下实测原始产物与一条可复跑命令；未闭合的如实登记，不用推测填充

## Comments

spec 的「前置验证闸门（开工第一步）」明确要求这三条在写实现之前用最小代价闭合。取证放在 `.scratch/voucher2t-mxz/` 下，与既有的 evidence 目录同规格。
