# 6. 并发提速与冲突科目的交互式清空重写

日期：2026-10-04
状态：已接受（实施待验收）

## 背景

round8 交付的脚本在真机上做了全量实测，暴露出两个问题。

**其一，慢。** 一轮完整运行要发约 932 次请求（抓取 136 + 清空 246 + 写入 550），全脚本零并发，29 处 `await` 全部串行。耗时构成有两笔账要分开算：

- 真机抓包（run `de6842d225c50`，round5）显示整轮人工操作跨度 752.8 秒，而其中 11 个 POST 合计只有 7896.9 毫秒、6 个 GET 合计 4750.3 毫秒 —— **网络往返约占 1%**，其余是人工停顿。这一轮不是耗时基准。
- 命令行版真提交一手日志（`out/fill-log-commit.txt:26→:319`）才是：全量 45 科目 408 行 `11:20:35.329Z → 11:29:26.264Z` = **530.9 秒（8.85 分钟）**，即 **1.30 秒/行**。其中 `insert` POST 实测均值约 685ms，按 417 行外推约 286 秒，**占写入阶段约 54%**；`CONFIG.throttleMs = 300` 是纯等待，417 行约 125 秒，占比约 25%。

仓库里原有一句「单科目写入耗时约 0.1-0.2 秒/行、全量 45 科目约 6 分钟」（`issues/09-end-to-end.md:59-60`、`map.md:56`）是 CLI **DOM 旧版**的口径，与上述现行日志不同量级，本 ADR 起不再引用。

**其二，冲突科目只能全清。** 平台该科目已有行、但与计划不匹配时，`fillAccount` 判 `stale`、本轮跳过该科目，并在日志提示「请先点①清空 T 型账，再重跑」。而「清空 T 型账」是**整轮扫全部 155 个总账科目**的重置动作 —— 为了三个科目写不进去，要把全平台清掉再重写全部 45 个。ADR-0004 当初删除配置项「先清空该科目再重写」是对的（它是个每次运行都要预先决定的开关），但删掉之后，这个诉求失去了任何出口。

## 决策

### 读路径 4 路并行

所有只读 GET 改为最多 4 路并发：凭证列表翻页与详情抓取、写前普查、清空阶段的逐科目前置查询。新增 `CONFIG.readConcurrency = 4`。

并行后**结果顺序必须与串行时逐项一致**：抓答案侧凭证时 `renumberAsAnswer` 用列表序号生成凭证字号 `记i+1`，顺序错乱会把凭证号写错。

### 写路径 3 路并发，粒度是科目

新增 `CONFIG.writeConcurrency = 3`。**同一科目内部严格串行，科目之间可以并行。**

这个不对称有实测依据，不是保守起见：

- **科目内必须串行**：`insert` 的请求体自带「当前已存全部行的 `pzh_bz`/`debit`/`lend`/`TEMPid`」，而 `TEMPid` 由服务端逐次生成、递增（真机 `post-bodies-1001.json`：首个 `insert` 体 134 字符只含 `_i` 三连；第 123 次起出现 `TEMPid=175176` 并递增）。下一行必须看到上一行的落库结果，`fillAccount` 里的 `let state` 就是这条依赖的载体。
- **科目间无依赖**：`state` 是 `fillAccount` 的局部变量；请求体自包含（`sxid`/`accountID`/`yyyy`/`mm`/`entityid` 每次显式携带），平台不靠会话游标记住「当前科目」。反证在 `fillAccount` 自身：它每科目先 GET 并断言 `q.state.accountID !== acc.code` 即显式失败。

### `throttleMs` 300 → 120

417 行省下约 75 秒。选 120 而非 0，是因为它与 round5 真机试写实跑过的值一致。

### 冲突科目：写前普查 → 日志清单 → 两个按钮

归集完成、三重锁通过之后、正式写入之前，**先并行普查平台全部 155 个科目**（一次 `/do` 查询就带全部科目下拉），按四类处置：

| 分类 | 判定 | 处置 |
|---|---|---|
| `none` | 平台 0 行 | 待写 |
| `ident` | 有行且与计划逐行匹配（沿用 `rowMatchesPlan` 宽容口径） | 幂等跳过 |
| `conflict` | 有行但不匹配 | 列入清单，等用户裁决 |
| `unknown` | GET 失败 | 本轮跳过该科目，最后单独报出 |

**`unknown` 绝不并入 `none`。** 「拿不到平台状态」与「平台是空的」是两回事，后者会直接叠写，而平台无事务、无回滚。

普查还顺带识别**计划外科目**（不在计划 45 个里、但平台有行）：只报出科目与行数，**不动它们** —— 它们可能是别的实习批次留下的数据，脚本不做超出用户意图的删除。

拿到冲突清单后在日志区列成纯文本（面板日志走 `textContent`，markdown 不渲染），每行形态 `科目码 科目名 ｜ 平台 N 行 / 计划 M 行`，并启用两个按钮「清掉这些科目并继续」/「跳过它们」。**冲突不再分级，一律清空该科目再重写**：平台 T 型账没有部分更新的语义，行与行之间没有稳定主键可供逐行对齐，分级判断只会把「上次写到一半」误判成「数据分歧」。

点「清掉」后**先并行删完所有冲突科目，再统一进入写入** —— 删除是预清理，不是写路径的一个分支。这让 `fillAccount` 维持单一形态（平台无行 → 写），不新增「有行变无行」的入口。

**不记住跳过**：本地不留「已跳过」状态。平台是唯一真相，下次运行重新普查、重新问。

### 进度行

普查 155 科目、清空 155 科目、抓取 103 凭证这三段长跑，各在日志区**原地刷新一行** `已查 N/总数`。ADR-0004 记过一个缺口（「面板只留日志区后，长跑期间没有任何进度提示」），这里补上。

### 停止语义：在途请求收完，不再发新的

并发下点「停止」，已发出的请求允许跑完，不再派发新任务。**不用 abort**：`GM_xmlhttpRequest` 中止后无法区分「被取消」与「请求失败」，会把重试逻辑带偏。

## 理由

- **并行收益集中在只读段，写入段的并行是有限的**。清空阶段 246 次请求里 201 次是 GET，改为并行后主体耗时消失；写入段 461 次 POST 里 417 次是逐行 `insert`，受 `TEMPid` 依赖约束**无法并行**，只能靠科目级并发摊薄（3 路后写入段理论降到约 1/3）。
- **不改用批量写入**。曾评估「一次 POST 写多行」这条结构性路线（417 次 → 45 次量级），**已在真机上试写证伪**：一次 `start=insert` 的请求体带**两组** `pzh_bz_i/debit_i/lend_i`（`记1/借111.00` 与 `记2/贷222.00`），服务端只取第一组 —— 响应里只出现 `记1 借 111.00`（TEMPid=176530），第二组**无报错、无痕迹地被丢弃**，HTTP 仍为 200，重渲染后的页面待填行仍只有一组。这个结果与离线取证一致：平台 T 型账页只渲染**一组**待填字段，校验函数 `script_check_debit_lend(#1, flag, index)` 对已存行按递增索引 `0..8` 取第 N 组、对 `_i` 待填行索引恒为 `'0'` —— 平台把「行」建模为无后缀重复字段（可 N 组），把「待填行」建模为**单槽** `_i`。抓包见 `.scratch/voucher2t-taccount/verify/raw/round9-batch-write/capture-batch-probe.json`；离线取证见同目录 `round9-batch-write-probe.md`。
  试写在科目 1701（无形资产）上完成，试后已用选择性删除把它恢复到试写前状态（仅 `记74 / 145000.00`）。
  ⚠ 试写过程中暴露出一个真实陷阱：查询该科目时若**漏掉 `sxid`/`entityid` 参数**，平台返回的是**假空态** —— 与「该科目确实是空的」在响应上无从区分。本脚本的 `queryTState` 一直带全参数，不受影响；但这条实测把「写前普查里 `unknown` 绝不能并入 `none`」从保守假设升格为有实证支撑的必要设计。
- **保留 `update_loop`**。离线取证发现：末次 `insert` 响应与 `update_loop` 响应**逐字节全等**（22940 === 22940），且与随后的读回 GET 也逐字全等，即 `update_loop` 前后 T 型账页渲染一个字符未变。但这条证据的覆盖面只到**T 型账页本身** —— 平台的「登账情况」列（`n/m`，服务端记录的逐凭证登账进度）在**另一个页签**里，该轮抓包全程未访问。无法排除 `update_loop` 正是更新那一列的那一步，而那一列是命令行版幂等判据依赖的权威信号。省它只省约 20 秒，不值得押这个不确定性。
- **并发路数取 4（读）/ 3（写）**：平台是单台 Tomcat 上的老式 jQuery 应用，从未做过压力测试；真机抓包 251 条请求全是 200、无 429/503，但「无限速证据」不等于「不会限速」。注释里那句「太小可能被平台拒绝」（脚本 `:71`）至今**没有实测支撑**。

## 代价

- **并发引入了新的失败形态**。串行时「停止」的边界是清晰的（行与行之间）；并发后存在「已派出、未返回」的窗口，其语义只能靠约定（在途收完），无法靠代码强制。
- **并行只读使日志顺序不再是服务端返回顺序**。要求「按输入顺序返回结果」来保住凭证字号，但这意味着日志里出现的时间顺序与真实请求顺序不同 —— 看日志排查时序问题时要注意这点。
- **写前普查把一轮的请求数又抬高了**：对全部 155 个科目各发一次只读 GET（现版是写入前对计划内科目各一次，共 45 次）。多出约 110 次只读请求换取「写入前就能看到完整冲突清单」，避免了「写了一半才发现冲突」。
- **「先删全部冲突科目、再统一写入」扩大了删除的作用面**。若删除成功而随后写入因锁或网络失败，平台会停在一个比运行前更空的状态。缓解手段仍只有日志与「停止」。
- **计划外科目只报不删**：若平台确实残留了大量无用数据，脚本不会帮你清，需要走「清空 T 型账」。这是刻意的边界。
- **`unknown` 科目在 WebVPN 网络抖动下会变多**，表现是「跑完了一部分科目没写」——比叠写好，但需要用户重试。

## 未决 / 下轮验证

- 并发路数 4/3 是**拍定的**，不是实测推出的：平台在任何节流或并发档位下都没有限速/拒绝的实测数据。
- 写前普查对 155 个科目发只读 GET 的真实耗时**未实测**（ADR-0004 时代曾标注过「155 次 GET 真机上可能达数分钟」，那也是推测）。
- 油猴版全量运行（HTTP 化 + 并发）的**净耗时基线缺失**：现有真机数据只有 round5 的 1001 单科目 9 行，与演练模式的 3 分钟（不含写入）。改造后的提速只能用「不快于改造前」来验收。
- 批量写入那条路（一次 POST 多行）**已闭合为不可行**（见「理由」段落的真机试写），不再列为未决项。
- 「登账情况」列（`n/m`）在本轮实训中的分子**仍然全空**（实测：记1 `/4`、记2 `/3`……），与 `map.md` 记的「分子恒空」一致 —— 因此 `update_loop` 是否更新该列**仍未验证**，保留它的理由仍是「不值得为 20 秒押这个不确定性」。
