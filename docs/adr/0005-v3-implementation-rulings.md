# 5. v3 实施的裁决：清空不过闸门、以及 4 处 ADR 未覆盖的冲突

日期：2026-10-04
状态：已接受（实施中）
上游：`docs/adr/0004-panel-interaction-v3.md`（面板交互 v3）

## 背景

ADR-0004 定下了 v3 的面板形态与行为，但实施过程中发现它与**已成文的旧决策**、以及**自身条文之间**存在若干未裁决的冲突。本 ADR 记录裁决结果，避免实施方各自即兴。

## 裁决一：清空 T 型账不过三锁闸门 —— ADR-0003 的 D7 断言作废

**冲突**：ADR-0003 的验收台 `impl/B-verify/http-write.mjs` 有一条 D7 断言「删除/写入的唯一入口都在『锁一/锁二未过即 return』之后调用（同一道闸门）」。而 ADR-0004 明说清空「**不依赖先抓到凭证，不过三锁**——清空是重置动作，凭证取不到时也应能用它把平台清干净」。

**裁决**：**ADR-0004 后发，以它为准。** D7 中 `callClear > gateReturn` 这一子条件不再成立，必须改写。

**理由**：两条决策服务的目的不同。闸门守的是「**写入**不能基于未通过校验的计划去改平台数据」；而清空**没有计划**——它的输入是平台自身的科目表，不存在「计划是否可信」这个问题。把清空也塞进闸门，会让「凭证抓不到 ⇒ 平台也清不掉」这个死角成立，而清空恰恰是那种情况下唯一的救援手段。

**代价**：清空是本项目**唯一**不受任何校验保护的破坏性动作。防线只剩一次不含科目数的确认弹窗（ADR-0004 已承认这点）。

**保留的强度**：写入侧的 `callFill > gateReturn` 断言**必须继续成立**，D7b（写路径段内 `submitForm` 的 start 值只有 `insert`/`update_loop`/`delete_loop` 三种）不变。删除侧改为断言清空是一条**不被 `lock.l1ok && lock.l2ok` 前置 return 拦断**的独立代码路径，且 `clearAllAccounts` 内部不引用 `lock.`/`l1ok`/`l2ok`。

## 裁决二：教师答案缓存的「批次不符提示」与「命中缓存静默」不冲突

**冲突**：ADR-0004 同时要求「命中缓存时静默复用，日志不额外说明」与「缓存记下取数时的实训批次，与当前批次不符时仅在日志提示」。

**裁决**：**两者作用于不同事件，都可实现。**

- 正常命中 ⇒ **不打任何缓存相关日志**（连「用本地缓存」都不说）。
- 批次不符 ⇒ 这是**例外情形**，必须打一条提示。

**理由**：「静默」约束的是「别向用户汇报缓存的内部机制」；批次不符是**数据可信度**问题，属于用户必须知道的事。把两者读成互斥，是把「不报机制」误读成「不报异常」。

## 裁决三：学生答案缓存同样记批次，回退键选 SXID 的代价要写进日志

**冲突**：ADR-0004 只给教师答案规定了批次校验，学生答案未写。

**裁决**：学生答案缓存**同样记 `entityID`**，同样「不符时仅提示」。隔离键取不到学号而回退 `SXID` 时，在**首次写入该缓存**时打一条提示说明键的来源。

**理由**：学生答案同样随批次变化（批次决定企业），不记批次会让「换了批次仍读旧学生答案」静默发生。回退键的来源必须可见——若 `SXID` 实际随会话变化，缓存将永不命中，用户需要能看出这一点而不是只看到「每次都重新抓」。

## 裁决四：停止的中间态 —— 「行已插满但未 `update_loop`」允许存在

**冲突**：ADR-0004 只定义「正在提交的那一行会写完」，未定义停止恰好落在「最后一行 `insert` 完成、`update_loop` 未执行」之间时的语义。

**裁决**：**允许该中间态存在，不额外补偿。** 但在日志中**明确报出**该科目处于「已插入 N 行、未做整体提交」状态。

**理由**：平台无事务，任何补偿动作（自动补一发 `update_loop`）都违背「停止后不再写」的语义，反而更危险。让它可见 + 让「清空」成为标准恢复路径，是本项目一贯的口径（复用 `stale` 分支的处理哲学：不自动覆盖，只告警）。

## 裁决五：连点按钮的串联后果 —— 记入手工测试清单，不改代码

**冲突**：清空不过闸门、写入过闸门 ⇒ 「凭证取不到 → 清空成功 → 写入被锁一/锁二拦下」会留下「平台被清空、一条没写回」的净损失状态。ADR-0004 只论证了单个按钮的合理性。

**裁决**：**不通过代码阻止该序列**（阻止需要引入耦合态，与「两个写入按钮并存、先写谁就以谁为准」的既定形态冲突）。改为在手工测试清单与日志中明确暴露：

- 写入被闸门拦下时，日志必须说清「平台未写入」——已有 `❌ 锁一/锁二未过，已停止，未写平台` 承担此职。
- 手工测试清单需覆盖「清空后写入失败」这一序列的可见性。

**理由**：净损失状态在**凭证本身取不到**时必然出现，而那时用户的第一诉求本就是「把平台清干净」。把它当错误阻止，会挡掉合法的重置用法。
